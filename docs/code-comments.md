# Code comments

Conventions for inline comments across all crates. Single source of truth for the
rules; per-language notes at the end.

## Rules

- **WHY, not HOW.** Comments explain intent, constraints, or trade-offs. The code
  already shows what it does.
- **No paraphrase of code.** A comment that restates the next line adds noise.
- **No commented-out code.** Delete it; git history preserves what was removed.
- **No section-banner comments** (e.g., `// ====== helpers ======`). If a file
  needs visual separation, split it.
- **TODO / FIXME must reference an issue**: `// TODO(#NNN): <short context>`. An
  undated, untracked TODO is dead code.
- **English only** (per the global rule in `CLAUDE.md`).
- **No emojis** (per the global rule).
- **No AI references** (Co-Authored-By, Generated by, etc. — per the global rule).

## When to write a comment

- Business/security rationale not derivable from the code (crypto invariant,
  performance trade-off measured in a profile, edge case learned from a real
  incident).
- A workaround for a known bug in a dependency, with a link to the upstream issue.
- A non-obvious invariant the next reader must preserve.

## When NOT to write a comment

- Restating what the code does.
- Documenting language features or standard-library behavior.
- Marking the obvious (`// increment counter` above `counter += 1`).

## Per-language notes

### Rust

Doc comments (`///`, `//!`) on public items where the name does not fully convey
the contract; keep them minimal — the type signature already describes most of the
API. Prefer documenting invariants and panics/errors over restating parameters.
For security-critical code (`core::crypto`, `core::sync`), a doc comment stating
the invariant that must hold is warranted even when the signature looks obvious.

### Kotlin (Android)

KDoc on public symbols where the name does not fully convey the contract. Keep it
minimal; one short sentence beats a multi-line block.
